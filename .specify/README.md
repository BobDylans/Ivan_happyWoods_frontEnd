## 📚 核心文档

### 📜 [constitution.md](constitution.md)
**项目宪法** - 定义项目的核心原则和约束

- ✅ 核心价值观（MUST/SHOULD/禁止事项）
- ✅ 技术架构原则
- ✅ 开发流程原则

**何时查看**:

### 📋 [spec.md](spec.md)

**何时查看**:

- 验收功能是否完成时

## 📖 文档使用流程

### 1️⃣ 开始新功能开发

```
1. 查看 spec.md → 了解功能需求
2. 查看 plan.md → 了解技术方案
3. 查看 tasks.md → 找到对应任务
4. 查看 constitution.md → 确认符合原则
5. 开始编码
```

### 2️⃣ 遇到技术决策

```
1. 查看 constitution.md → 是否有明确规定？
2. 查看 plan.md → 是否有类似决策？
3. 查看 memory.md → 过去是否有类似情况？
4. 做出决策并记录
```

### 3️⃣ 完成任务

```
1. 查看 tasks.md → 确认验收标准
2. 更新任务状态为"已完成"
3. 如有重要决策，更新 memory.md
4. 提交代码
```

### 4️⃣ 规划下一步

```
1. 查看 tasks.md → 查看未开始任务
2. 查看 plan.md → 确认当前阶段
3. 选择优先级最高的任务
4. 回到流程 1
```

## 🤝 如何贡献

### 修改文档

1. **小改动**（错别字、格式）：直接修改并提交
2. **中等改动**（添加任务、更新进度）：修改后通知团队
3. **大改动**（修改宪法、重构计划）：需要团队讨论和投票

### 提议新文档

如果需要添加新的规范文档：

1. 在 Issue 中提出建议
2. 说明文档用途和结构
3. 团队讨论通过后创建
4. 更新本 README

## 📞 常见问题

### Q: 为什么要这么详细的文档？

**A**: 规范驱动开发的优势：
- ✅ 减少沟通成本
- ✅ 新成员快速上手
- ✅ 决策有据可查
- ✅ 减少返工

### Q: 文档会不会过时？

**A**: 我们的策略：
- 📅 定期审查（每周/每月）
- 🔄 及时更新
- 📝 记录变更历史
- ⚠️ 标记过期内容

### Q: 如果文档和代码冲突？

**A**: 优先级：
1. 代码是事实，文档可能滞后
2. 及时更新文档以匹配代码
3. 如果代码违反宪法，修改代码
4. 记录差异原因
